Grant money that moves when the work does.

Tranche escrows a grant in milestones. Each tranche is released when its terms are met: checked in code where the question is decidable, judged by a validator jury where it is not. No program manager reads the pull request. Neither side can take the money back while the other is waiting on a ruling.

The problem

Every grant program is a review queue.

A funder pays in milestones because nobody wants to pay for work that never ships. So each milestone waits for a person to open the repository, decide whether it matches what was promised, and release the next payment. The person holding the money is the person judging the work, and the builder waits on their calendar.

Most of what a milestone promises is checkable: the directory exists, the test file is there, the release has the right number of entries. A smaller part needs reading — is the README actually documentation, does the API do what the brief said. Tranche separates the two, runs the first in code and sends only the second to a jury.

How a grant runs

01OpenThe funder escrows the full grant and names the builder. Tranches and their terms are fixed up front.
02SubmitOnly the builder, only the current tranche, only evidence pinned to a commit SHA.
03SettleMechanical terms checked in code. The jury runs only if they all pass and judged terms remain.
04FinalizeApproved: paid, next tranche opens. Rejected: back to the builder to try again.
05or AppealThe side the ruling went against stakes a bond equal to the tranche for a fresh review.

A rejection does not refund the funder. The tranche stays escrowed for the builder's next attempt; the funder can only withdraw what has not been delivered, and only while nothing is under review.

Terms

Written per tranche, before any work starts. A term with a kind prefix is mechanical. Anything else is judged.

// tranche 0 — scaffold, 0.1 GEN
contains: tranche.py
contains: README.md
// tranche 1 — tests and docs, 0.2 GEN
array_min: $ >= 5
contains: tests
the README explains how to verify a deployment     ← judged

Mechanical — decided in code

contains, json_equals, json_exists, array_min. Evaluated in deterministic Python after one consensus fetch, so every validator computes the same answer from the same bytes. If one fails, the jury is never convened.

Judged — decided by the jury

One boolean per term, and every validator must agree on every one. The jury returns nothing else: free text in a compared answer prevents consensus even when the verdicts are identical.

What protects whom

The builder

The full grant is escrowed at opening, so it exists. The funder cannot cancel while a tranche is submitted, under review, ruled or under appeal. A rejection keeps the tranche open for another attempt rather than refunding it.

The funder

Tranches are delivered in order and only by the named builder. Evidence must pin a 40-character commit SHA, so it cannot be edited after submission. An approval can be appealed like a rejection.

Both, from bad evidence

A fetch that fills the reading window is refused as INCONCLUSIVE — validators shown a truncated artifact agree unanimously on false answers. A fetch that returns a rate-limit notice or an API error instead of the artifact is refused as INADMISSIBLE, and settle can simply be called again.

Both, from a bad ruling

Appealing costs a bond equal to the tranche. Overturned, the appellant gets it back. Upheld, it goes to the other side. Contesting a correct ruling is expensive, contesting a wrong one is free.

Lineage

Tranche is the third contract in a line, and reuses what the first two proved on chain rather than rewriting it.

BountyCourtEscrow that follows a per-criterion verdict, appeals with bonds, refusal to rule on truncated evidence, refusal to rule on an error response.
